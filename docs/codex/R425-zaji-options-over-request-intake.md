# R425 요청에서 가져온 접수에는 작지가 옵션만 얹는다

상태: 구현 완료, 빌드 통과, 화면 확인 미완. 클로드가 직접 시공했다(2026-11-12).

2026-11-12 박향근 확정이다.

> DD 작성할때는 기본적으로 작지 발행한 후에 입력하기 때문에 request에서 가져오는 행위와 작지 업로드 행위가 거의 같은 시점이다. request에서 먼저 가져왔으면 작지는 옵션만 파싱하는걸로 하고 request 없이 작지를 먼저 넣으면 작지가 기존대로 전체 반영하는걸로 하자.

## 무엇이 문제였나

신규 작지 접수 창에서 두 길이 **배타**였다. 작지를 첨부하면 `onAttachFile`이 접수 초안을 통째로 작지 레코드로 갈아치우고 `setIntakeRequest(null)`로 의뢰 연결을 끊었다. 실무에서는 작지가 나온 뒤에 DD를 쓰므로 요청 불러오기와 작지 첨부가 거의 같은 시점인데, 둘째 동작이 첫째를 지웠다. 그래서 보드와 DD가 갈라졌다.

## 정한 규칙

| 상황 | 작지 첨부의 동작 |
|---|---|
| **요청에서 먼저 가져온 접수** (`intakeRequest`가 있고 접수 행이 있다) | 작지는 **옵션만** 얹는다. 의뢰 연결과 공통 칸을 지킨다 |
| **요청 없이 작지부터** | 예전 그대로 전부 반영하고 연결은 없다 |

옵션만 얹을 때 바뀌는 값은 `applyZajiOption`이 손대는 것 전부다. 색상, 중량, 조직, 염색, 비고, `tech.yarnDetail`, `tech.mills`, `tech.bodyNo`, `tech.intakeSource`다. **작지가 이긴다.** 그것이 작지 우선 원칙이다.

공통 칸은 `fillZajiHeaderBlanks`로 **빈 칸만** 채운다. Style No., Season, 납기, SA No., 개발처, 개발 담당, ORIGINAL Brand다. 의뢰에서 온 값을 덮지 않는다. **Season과 납기는 의뢰에 없고 작지에 있어서 이 경로가 필요하다.** 보드 이름으로 Season과 Category를 채우지 않는 기존 결정 때문에 요청 불러오기만으로는 그 칸이 늘 빈다. Category는 작지에도 없어 사람이 고른다.

## 짝 짓기

순서대로 짓는다. 둘 중 적은 수만큼 짝이 된다.

- 작지 옵션이 더 많으면 **행으로 더한다.** 그 행에는 짝이 될 의뢰 옵션이 없으므로 `tech.requestLink`를 떼고 넣는다. 공통 칸은 `applySharedFields`로 첫 행에서 물려받는다.
- 접수 행이 더 많으면 **그대로 둔다.** 지우지 않는다.
- 건수는 세 문장으로 `setIntakeNotice`에 적는다. 저장을 막지 않는다.

**순서 말고 다른 키로 짝을 짓지 마라.** 작지는 Part+Color가 옵션 단위이고(R114) 의뢰는 `lineId`다. 둘 사이에 공통 키가 없다. 개수가 같다고 같은 옵션이라는 보장도 없으므로, 화면에서 사람이 확인하는 것이 마지막 관문이다. 저장 전에 옵션 그리드가 그대로 보인다.

## 역순서 안내

작지를 붙인 뒤 「DEVELOPMENT REQUEST에서 불러오기」를 누르면 `importRequest`가 `resetAttach()`로 **아무 말 없이** 작지를 버렸다. 반대 방향은 문구가 뜨는데 이쪽은 없었다. 이제 안내 문구를 띄운다. 동작은 그대로 버리는 것이다. 요청을 먼저 불러온 뒤 작지를 첨부하면 위 규칙대로 합쳐진다.

## 뒤집지 말 것

- **`applyZajiHeader`와 `fillZajiHeaderBlanks`를 한 함수로 합치지 마라.** 앞은 전부 덮고 뒤는 빈 칸만 채운다. 쓰는 자리가 다르다.
- **작지 옵션 값이 의뢰 값을 이긴다.** 이 방향을 뒤집지 마라.
- **공통 칸은 의뢰가 이긴다.** 작지가 덮게 하지 마라.
- 짝을 순서 말고 다른 키로 짓지 마라.
- 접수 행을 지우지 마라.
- `tech.intakeSource`가 작지 출처로 바뀐다. 중복 접수 검사(`useAppStore`의 `intakeSourceKey`)가 작지 키를 먼저 본다. 의도한 결과다.

## 검증

`npm run build` 통과. `tsc --noEmit` 포함이다.

화면 확인은 박향근이 한다. 보는 순서는 이렇다.

1. DD MASTER 신규 작지 접수에서 「DEVELOPMENT REQUEST에서 불러오기」로 옵션 여러 건을 가져온다.
2. 그 상태에서 「작업지시서 첨부」로 같은 건의 작지를 올린다.
3. 상단 REQUEST 칩이 그대로 있는지, 옵션 값이 작지 값으로 바뀌었는지, Season과 납기가 찼는지 본다.
4. 안내 문구에 적힌 건수가 작지 옵션 수와 맞는지 본다.

## 남은 것

이 작업은 접수 창 안에서만이다. **이미 저장된 DD 행에 작지를 다시 얹는 길은 없다.** 그 건은 따로 뗀다.

# R240 팀 공유 저장 유실 차단: 병합 키 트랜잭션 저장, 샘플대장 병합

상태: 구현, 검증 완료(2026-09-22). 코덱스 없이 클로드가 직접 구현했다. 동기화는 한 글자가 유실로 이어지는 구간이라 설명 비용이 구현 비용보다 컸다.

## 무엇이 잃고 있었나

1. **병합 키도 경합에서 잃었다.** `pushCacheNow`가 마지막으로 받은 스냅샷(`lastRemote`)과 병합해 `writeBatch`로 서버 문서를 통째로 덮었다. B가 먼저 저장하고 그 스냅샷이 A에게 닿기 전에 A가 저장하면, A의 쓰기에서 B의 항목이 빠진다. B 화면은 다음 스냅샷에서 그 항목을 "원격에서 지워졌다"로 읽고 스스로 지운다. `records`, `fabricOverrides`, `fabricEvents` 모두 해당.
2. **대기열 속 옛 값.** 키별 전송 대기열에서 기다리는 사이 스냅샷이 기준선을 새로 바꿨는데 예전 값을 올리면, 그 사이 팀원이 넣은 항목을 내가 지운 것으로 읽었다.
3. **`completed`(샘플대장)는 병합 키가 아니었다.** 1팀 원단 본문(FL, Color, Content 등)과 3팀 직접 추가 행이 여기 산다. 1팀 15개 계정이 라이브로 입고하면 마지막 저장이 배열을 통째로 덮었다. `buildFabricLedger`는 샘플이 없는 창고 상태와 이력을 조용히 버리므로(668, 686행) 원단이 통째로 사라진다.
4. **샘플대장 재업로드가 1팀 행을 버렸다.** `ingestSamples`가 웹 등록 행만 살려 붙였다.
5. 빈 배열 한 번이 서버를 비울 수 있었고, 전송 실패는 조용히 버려졌다.

## 틀렸던 판단 (다시 시도하지 말 것)

- "병합 키만 늘리면 된다." 아니다. 쓰기가 서버 최신값을 보지 않으면 병합 키도 잃는다(위 1번).
- "`completed`는 `id`로 병합하면 된다." 아니다. 옛 대장 행 id가 `rnd:번호`라 5,497행 중 401그룹 740행이 id를 공유한다. id로 병합하면 겹친 행이 서로를 지운다. `시트|id`로도 740행이 겹친다(같은 시트 안 채번 주기 반복).

## 검증

- 실제 `firestore-sync.ts`를 가짜 Firestore(트랜잭션 버전 검사 포함)에 붙여 클라이언트 3개로 9개 시나리오 20개 검사: 스냅샷 지연 중 동시 입고, 3명 동시 트랜잭션, 대기열 속 옛 값, 편집과 추가 겹침, 삭제 전파와 동시 추가, 대장 재업로드와 동시 입고, 빈 배열, 전송 실패 재시도, 비병합 키.
  - 새 코드 20건 통과. **같은 테스트에서 옛 코드는 8건 실패**(한 건 유실, 세 건 중 두 건 유실, 편집 유실, 삭제 부활, 재업로드 유실, 빈 배열로 서버 비움, 알림 없음).
- 실제 Firestore: `fabricOverrides`, `completed`(22청크, 4.4MB)에 같은 값 저장을 트랜잭션으로 보내 커밋 확인. 서버 값이 저장 전 백업과 한 글자도 다르지 않음, 남는 옛 청크 없음, 규칙 거부 없음.
- `npm run build` 통과.

## 남은 위험

- 배포 전에 열려 있던 옛 탭은 옛 방식으로 쓴다. 배포 뒤 팀 전원 새로 고침이 필요하다.
- 끝내 실패한 저장은 새로 고치면 사라진다(첫 스냅샷이 로컬을 서버 값으로 바꾼다). 경고 문구로 막는다. 근본책은 기준선을 IndexedDB에 저장하는 것.
- 비병합 키(`ts`, `study`, `events` 등)는 마지막 저장이 이긴다. TS는 손실 이력이 있다.
- 커밋 요청 크기 한도 10 MiB. `completed` 4.4MB.

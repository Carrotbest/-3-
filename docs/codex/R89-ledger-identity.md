# R89 — 원장 식별 규칙 수정 (행 절반이 사라지는 버그)

상태: 미착수. **데이터 버그다. 화면 작업보다 먼저 한다.**

## 무엇이 잘못됐나

`src/data/fabric-ledger.ts` 의 `buildFabricLedger`(200행)에 이 줄이 있다.

    const matchedKey = items.has(directKey) ? directKey : styleIndex.get(styleKey) ?? directKey

FL 로 만든 고유 키가 아직 등록 전이면 **Style 로 남의 항목을 찾아간다.**
대장은 같은 Style 에 색상별·FL별로 여러 행이 있는 구조라, 뒤 행이 앞 행에 통째로 흡수된다.

실측이다. 사용자의 실제 대장 파일로 앱 로직을 재현해 얻은 값이다.

    대장 원본        5,190행
    현재 결과        2,462건   (53% 소실)
    창고보관 653행 →   269건

고유 FL 을 가졌는데도 Style 때문에 삼켜진 행이 2,105행이다.
창고보관 312, 소진완료 105, 폐기 1,688.
FL 중복은 42건뿐이므로 **문제의 98%가 이 한 줄이다.**

## 무엇으로 바꾸나

R&D No.(`storageNo`)가 실물 하나를 가리키는 진짜 식별자다.
확인한 사실이다. 창고보관 653행의 R&D No. 가 **653개 전부 고유하다.**
사용자도 "입고 단위는 DD 행 하나"라고 확정했다.

수정 후 예상값이다. 이 숫자와 다르면 뭔가 잘못된 것이다.

    총 4,771건 | 창고보관 653건

## 1. 식별 규칙

각 행의 **자기 식별자**를 이 순서로 정한다.

    rnd:<storageNo>   R&D No. 가 있으면 이것
    fl:<FL>           없고 FL 이 있으면 이것
    style:<STYLE>     둘 다 없으면 이것
    source:<fallback> 아무것도 없으면 이것

정규화는 기존 `normalized`(57행)를 그대로 쓴다.

**항목 하나가 여러 식별자를 가질 수 있다.** 예를 들어 R&D No. 0412 이면서 FL26080012 인 행은
`rnd:0412` 와 `fl:FL26080012` 를 둘 다 갖는다.

그래서 `styleIndex` 하나를 `identityIndex: Map<string, string>` 하나로 바꾼다.
식별자 문자열에서 항목 key 를 찾는 색인이다.
항목을 만들거나 병합할 때마다 그 항목이 아는 식별자(rnd, fl, style)를 전부 등록한다.

## 2. 병합 규칙

들어온 행을 어디에 붙일지 정하는 규칙이다.

1. 자기 식별자로 `identityIndex` 를 찾는다. 있으면 그 항목에 병합한다.
2. 없고, **그 행에 R&D No. 가 없으면** FL 식별자로, 다음 Style 식별자로 찾아본다.
3. 없고, **그 행에 R&D No. 가 있으면** 다른 식별자로 찾지 않는다. 새 항목을 만든다.

**3번이 이번 수정의 핵심이다.** R&D No. 가 있다는 것은 창고에 실물이 하나 있다는 뜻이다.
Style 이 같다는 이유로 다른 실물과 합쳐지면 안 된다.

동시에 그 항목의 FL 은 색인에 등록한다. 그래야 DD 레코드가 FL 로 찾아와 붙는다.
**이걸 빠뜨리면 DD MASTER 와 창고의 연결이 통째로 끊긴다.** 반드시 등록해라.

DD 레코드는 R&D No. 가 없으므로 2번 경로를 탄다. 지금과 같다.

## 3. 기존 웹 기록을 잃지 않는다

여기가 가장 위험한 부분이다.

`fabricOverrides` 와 `fabricEvents` 는 `fabricKey` 로 항목에 붙는다.
키 문자열이 `fl:...` 에서 `rnd:...` 로 바뀌면 **팀이 웹에서 등록한 출고·폐기·재고 기록이
전부 연결을 잃는다.** 화면에서 조용히 사라진다.

**호환 해석을 넣어라.**

  - 오버라이드와 이벤트를 적용할 때, `fabricKey` 가 지금 항목 중 어디에도 없으면
    그 값을 `identityIndex` 에서 다시 찾아라. 옛 키는 `fl:` 나 `style:` 형태이고
    새 항목도 그 식별자를 색인에 등록해 두었으므로 찾아진다.
  - 찾으면 그 항목에 붙인다. 못 찾으면 지금처럼 조용히 버린다.

**저장된 기록을 고쳐 쓰지 마라.** 마이그레이션이나 일괄 갱신 코드를 만들지 마라.
읽을 때 해석만 한다. 되돌릴 수 있어야 한다.

한 가지 부작용을 알고 있어라. 옛 키 `fl:X` 하나가 이제 여러 항목으로 갈라진 경우,
그 기록은 색인이 가리키는 항목 하나에만 붙는다. 정확히 어느 실물이었는지는
옛 데이터에 없으므로 복원할 수 없다. 그게 맞는 처리다. 임의로 나눠 붙이지 마라.

## 4. 상태 병합은 건드리지 마라

`mergeSample`(177행)의 이 줄은 그대로 둔다.

    status: statusRank[sampleStatus] > statusRank[target.status] ? sampleStatus : target.status

시트 간 FL 충돌은 7건뿐이라 이번 수정 뒤에는 거의 발생하지 않는다.
지금 손대면 변수가 늘어난다.

## 검증

- npm run build 를 통과시켜라.
- **R&D No. 를 가진 행이 Style 이나 FL 때문에 다른 항목에 흡수되지 않는지**
  코드로 확인하고 주석으로 남겨라. 이번 수정의 전부다.
- R&D No. 를 가진 항목의 FL 이 색인에 등록되는지 확인해라.
  빠지면 DD MASTER 연결이 끊긴다.
- 옛 키로 저장된 이벤트가 새 항목을 찾아가는 경로를 주석으로 남겨라.

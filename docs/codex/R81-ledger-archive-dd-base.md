# R81. 샘플관리대장 아카이브 고정과 DD MASTER 기준 전환

상태: **설계 완료, 컷오버 2026-09-02 확정**. Codex가 구현한다.

R76~R80은 완료·검증 끝났다. 이 문서는 그 위에 얹는다.

`npm run build` 통과를 유지한다. 커밋과 푸시는 하지 않는다.

**컷오버는 2026-09-02부터다.** 1~7절을 먼저 구현한다.
8절(아카이브 파일 커밋)은 사용자가 컷오버 시점 대장으로 파일을 만들어 지시할 때 진행한다.

---

# 배경: 두 파일은 다른 개념이다

이걸 먼저 짚어야 설계가 어긋나지 않는다.

- **샘플관리대장** — 팀 전체 샘플을 한 곳에 리스트업한 목록. 2015년부터 쌓였다
- **DD (Development Dashboard)** — 담당자별 탭에서 각자 현황을 관리하는 새 시스템

내용은 비슷해 보이지만 성격이 다르다. 두 파일의 Style 번호 체계가 아예 다르고 교집합이 없다.
**억지로 1:1 대응시키려 하지 마라.** FL 번호가 있는 건만 자연스럽게 겹친다.

앞으로 대장은 갱신하지 않는다. DD가 현황 관리를 맡고, 그 DD를 웹 대시보드로 이관하는 중이다.

## 실측 (2026-09-01 기준)

**샘플관리대장** 4시트 5,208 데이터행

| 시트 | 행 | 웹 상태 매핑 |
|---|---|---|
| 현황 | 54 | READY |
| 창고보관 | 649 | WAREHOUSE |
| 소진완료 | 403 | EXHAUSTED |
| 폐기 | 4,102 | DISPOSED |

시트명 네 개가 `fabric-ledger.ts`의 `statusFromSample()` 매칭어와 정확히 일치한다. 건드리지 마라.

- 고유 FL 3,598개, 기간 2015-01 ~ 2026-09

- 현황 시트는 FL이 0건이다. 아직 부여 전 단계다
- JSON 변환 시 약 1.84 MB (공백 제거 기준)

# 1. 병합 규칙에서 컷오프를 없앤다

## 지금

`mergedFlRegistrations()`(`derive.ts:1036`)가 `RDDA_ARCHIVE_CUTOFF_MONTH = "2026-07"`로 원천을 자른다.
대장은 그 이하만, DD는 초과만 넣는다. 양쪽 다 잘려 나가는 구간이 생긴다.

## 바꿀 것

컷오프로 **버리지 않는다.** 대장 전부를 넣고, DD 중 대장에 없는 FL을 더한다.
중복은 FL 키(`normalizeFlKey`)로만 판정하고 대장을 우선한다.

```
1. 대장 아카이브의 모든 FL을 넣는다. 월은 FL 인코딩(rddaMonthFromFlNo)에서 읽는다.
2. DD의 FL 중 아직 없는 것을 더한다. 월은 Received Date에서 읽는다.
3. 월 조건으로 건너뛰는 분기(1044행, 1053행)를 제거한다.
```

## 검증 기준

시뮬레이션 결과다. 이 수치를 구현 후 대조해라.

| | 등록 건수 |
|---|---|
| 현행 규칙 | 3,596 |
| 제안 규칙 | 3,601 |
| 늘어남 | +5 (전부 대장 2026-09, 창고보관 시트) |
| 사라짐 | **0** |

늘어나는 5건은 대장에는 있는데 DD에 아직 반영되지 않은 건이다.
사용자가 DD를 업데이트하면 DD 쪽으로도 들어오지만, 어느 쪽이든 이 규칙에서는 한 번만 잡힌다.

## 상수를 지우고 원천을 실제 값에서 읽는다

`RDDA_ARCHIVE_CUTOFF_MONTH`의 유일한 남은 소비처는 `monthlyDevelopmentTrend`(973행)의
`source: "샘플대장" | "DD"` 라벨이다. 이 라벨은 `Home.tsx:691`의 RDDA 툴팁에 배지로 표시된다.

**컷오버가 2026-09-02라서 월 비교로는 라벨을 못 만든다.** 9월은 대장에서 온 건과
DD에서 온 건이 같은 달에 섞인다. 월 경계와 컷오버 경계가 어긋나기 때문이다.

그래서 상수를 지우고, 그 달에 실제로 들어온 등록의 원천에서 라벨을 만든다.
`mergedFlRegistrations()`가 이미 등록마다 `source: "ledger" | "dd"`를 갖고 있으니 그걸 쓴다.

```ts
source: "DD" | "샘플대장" | "혼합"
```

- 그 달 등록이 전부 대장이면 `샘플대장`
- 전부 DD면 `DD`
- 둘 다 있으면 `혼합`
- 등록이 없는 달은 `DD`로 둔다. 앞으로는 DD가 원천이다

`MonthlyDevelopmentDatum.source` 타입(`derive.ts:211`)에 `"혼합"`을 추가한다.
`Home.tsx:691`의 배지는 값을 그대로 뿌리므로 별도 수정이 필요 없다.

**`RDDA_ARCHIVE_CUTOFF_MONTH`는 완전히 제거한다.** 다른 소비처가 없다.

# 2. 아카이브 파일은 앱이 만든다

**별도 변환 스크립트를 만들지 마라.** 파이썬으로 헤더 이름 매칭을 시도했더니
날짜 컬럼에서 엉뚱한 값이 나왔다. 시트마다 열 구성과 날짜 형식이 흔들린다.

앱에는 이미 `parseSamples()`(`xlsx-parsers.ts:730`)가 있고
"헤더 위치와 표기 흔들림을 흡수한다"는 주석대로 실전에서 검증됐다.
앱이 읽는 값과 파일에 박힌 값이 어긋나면 안 되므로, **같은 파서로 만든다.**

## 내보내기 기능

설정 화면(관리자 전용)에 버튼을 하나 만든다.

1. 대장 엑셀을 고른다
2. `parseSamples()`로 파싱한다
3. `CompletedSample[]`을 JSON으로 직렬화해 파일로 내려받는다
4. 사용자가 그 파일을 저장소에 넣는다

형식은 이렇게 한다. 배열만 두지 말고 봉투를 씌워야 나중에 판별이 된다.

```json
{
  "generatedAt": "2026-09-__T__:__:__Z",
  "sourceFile": "샘플 관리 대장.xlsx",
  "cutoverDate": "2026-09-02",
  "count": 5208,
  "samples": [ … ]
}
```

경로는 `public/data/ledger/archive.json`이다.

# 3. 아카이브를 읽는 경로

`src/data/ledger-archive.ts`를 새로 만든다.

```ts
export async function loadLedgerArchive(): Promise<CompletedSample[]>
```

`src/data/trend.ts`의 `readJson()`과 같은 방식으로 만든다.
`!res.ok`와 예외 모두에서 빈 배열을 돌려준다. **파일이 없어도 앱이 떠야 한다.**

## 우선순위 — 가장 중요하다

앱 시작 시 아카이브를 불러 `completed`에 넣는다. **아카이브가 무조건 이긴다.**

팀원 브라우저 IndexedDB에는 예전에 동기화된 대장이 남아 있다.
아카이브가 그걸 확실히 덮지 않으면 사람마다 다른 과거 데이터를 보게 된다.
불러온 뒤 `saveCacheLocal("completed", archive)`로 로컬 캐시도 아카이브로 맞춘다.

`saveCache`가 아니라 `saveCacheLocal`이다. Firestore로 다시 올리면 안 된다.

---

# 4. Firestore 동기화에서 대장을 뺀다

`src/data/firestore-sync.ts:67`에 이미 자리가 있다.

```ts
const SKIP_SYNC_KEYS = new Set<string>(["completed"])
```

이러면 소유자가 올리지도, 팀원이 받지도 않는다. 아카이브 파일이 유일한 원천이 된다.

Firestore에 남아 있는 기존 `completed` 문서는 사용자가 콘솔에서 지운다.
Codex는 건드리지 마라. 안 지우면 나중에 누가 `SKIP_SYNC_KEYS`에서 빼는 순간 되살아난다.

---

# 5. 상태는 웹이 이어받는다 (이미 구조가 있다)

새로 만들 게 없다. 확인만 해라.

- `statusFromSample()`이 시트명에서 **초기 상태**를 읽는다
- `fabricOverrides`가 웹에서 바꾼 상태로 **덮어쓴다**
- `buildFabricLedger():231`에서 오버라이드가 무조건 이긴다
- `fabricEvents`가 출고·소진·폐기 이력을 남긴다

즉 아카이브는 "컷오버 시점의 상태"를 초기값으로 주고, 그 뒤 변화는 창고 화면이 받는다.
대장 엑셀이 갱신되지 않아도 화면은 계속 살아 있다.

**나중에 관리자가 아카이브를 다시 만들어 교체해도 오버라이드가 이기므로,
웹에서 처리한 소진·폐기가 되살아나지 않는다.** 이 성질을 깨뜨리는 변경을 하지 마라.

# 6. 업로드 버튼을 옮긴다

**샘플대장 업로드 버튼은 다섯 군데에 있다. 전부 제거한다.**

| 파일 | 행 |
|---|---|
| `src/routes/Home.tsx` | 840 |
| `src/routes/Development.tsx` | 698 |
| `src/routes/Development.tsx` | 1471 |
| `src/routes/DevelopmentMasterSheet.tsx` | 1968 |
| `src/routes/Warehouse.tsx` | 570 |

행 번호는 참고용이다. `label="샘플대장 업로드"`로 찾아라.
**DD 업로드 버튼은 다섯 곳 모두 그대로 둔다.** DD는 계속 올린다.

설정 화면으로 옮기고 관리자에게만 보인다. 소유자 판정은 `currentUserIsOwner()`를 쓴다.
2절의 아카이브 내보내기 버튼도 같은 자리에 둔다.

대장을 더 이상 갱신하지 않기로 했으므로, HOME에 버튼이 남아 있으면
누군가 올려서 아카이브를 덮는다.

# 7. 화면 양식 통일

목록은 DD MASTER 양식을 따른다. 대장 고유 필드는 목록에서 빼고 상세에서만 보여 준다.

| 자리 | 내용 |
|---|---|
| 목록 공통 | `styleNo`, `flNo`, `season`, `category`, `buyer`, `owner`, `construction` |
| 상세 · 대장 원천 | `storageNo`, 공정(원사·편직·염색·가공), 물성(폭·중량·수축·필링), `completedAt` |
| 상세 · DD 원천 | `stage`, `dueDate`, `devStatus`, `processReached`, `receivedDate` |

원천 배지(`샘플대장` / `DD`)를 상세에 표시해 어디서 온 값인지 알 수 있게 한다.
`completedLibrary()`가 이미 `source` 필드를 갖고 있으니 그대로 쓴다.

# 8. 아카이브 커밋 (사용자 지시 후)

**사용자가 아카이브 파일을 만들어 지시하기 전에는 하지 마라.** 1~7절과 분리된 단계다.

절차는 이렇다.

1. 사용자가 컷오버 시점의 대장으로 아카이브 JSON을 내보낸다
2. `public/data/ledger/archive.json`에 넣는다
3. 커밋 전에 **실제로 올라갈 파일을 사용자에게 보여주고 확인받는다**

## 알고 있어야 할 것

이 저장소는 공개다. 아카이브에는 바이어명, 담당자 실명, 스타일·FL 번호,
공정 정보, 물성 실측값이 들어간다. 사용자가 이를 알고 실명 그대로 넣기로 결정했다.
퇴사자는 기존 익명화 규칙을 그대로 적용한다.

깃 히스토리는 영구다. 한 번 푸시되면 나중에 지워도 히스토리와 복제본에는 남는다.

# 검증

```
npm run build
```

1. `mergedFlRegistrations()` 결과가 3,601건인가. 현행 3,596에서 5건 늘고 0건 줄었는가

## 하지 말 것

- 별도 파이썬·Node 변환 스크립트를 만드는 것. 앱의 `parseSamples()`를 쓴다

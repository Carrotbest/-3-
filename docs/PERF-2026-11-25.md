# 성능 점검 (2026-11-25)

클로드와 코덱스가 서로 모르게 따로 보고, 겹치는 것만 확정했다. 고친 것은 없다. 진단만이다.

측정은 이 PC의 node 에서 재어서, 실제 브라우저는 보통 이보다 2배에서 4배 느리다. 행 수가 들어가는 계산은 800행을 가정했다. 실제 DD 행 수는 Firestore 에 있어 여기서 못 쟀다.

---

## 한 줄 요약

느린 자리가 셋이다. 첫 로딩은 **안 쓰는 데이터 5MB를 받느라** 느리고, DD 입력은 **셀 하나 고칠 때마다 모든 행 객체를 새로 만들어 표 전체를 다시 그리느라** 느리고, 팀원이 뭘 고칠 때마다 **모두의 브라우저가 25개 키를 통째로 다시 파싱하느라** 멈춘다.

가장 싸게 가장 크게 버는 것은 맨 아래 **즉시 고칠 것** 세 줄이다. 한 줄씩이고 구조를 안 건드린다.

## 1. 셀 하나를 고치면 모든 행 객체가 새로 만들어진다 (가장 큼)

`src/data/dd-workflow.ts:206`

```
return { ...record, devStatus, opt: ..., stage, processReached, tech }
```

`recalculateDevelopmentRecords` 가 `records.map` 안에서 **조건 없이** 새 객체를 돌려준다. 안 바뀐 행도 똑같이 새 객체다. 중첩된 `tech` 도 새로 만든다. 이 함수는 셀을 확정할 때마다 돈다(`useAppStore.ts:808`).

그래서 벌어지는 일이 넷이다.

**첫째, `GridCell` 의 `memo` 가 편집에서는 아무 일도 안 한다.** `DevelopmentMasterSheet.tsx:1476` 의 주석은 "선택이 한 칸 움직일 때 표 전체가 다시 그려지지 않도록"이라고 적혀 있고, 선택 이동에서는 실제로 막아 준다. 그때는 `record` 참조가 그대로이기 때문이다. 그런데 편집에서는 모든 행의 `record` 가 새 참조라 **74열 x 전체 행이 한 칸도 빠짐없이 다시 그려진다.** 800행이면 약 59,000칸이다. 설계는 맞는데 전제가 깨져 있다.

**둘째, 감사 기록이 전 행을 평탄화한다.** `audit.ts:118` `diffByKey` 에 `old === item` 이면 건너뛰는 분기가 없다. 있어도 참조가 늘 달라서 안 걸린다. 그래서 셀 하나 고칠 때마다 모든 행의 중첩 객체를 두 번씩 문자열로 펴 본다.

**셋째, 창고 대장이 통째로 다시 만들어진다.** `DevelopmentMasterSheet.tsx:1674` 의 `buildFabricLedger(records, samples, ...)` 가 `records` 참조를 보는데 그것이 매번 바뀐다. 5,190건짜리 `samples` 를 매번 다시 훑는다.

**넷째, 그 결과로 `ordered` 가 다시 걸러지고 다시 정렬된다.** 아래 2번과 3번의 비용이 여기에 그대로 얹힌다.

**고치는 방향.** `recalculateDevelopmentRecords` 가 계산 결과가 이전과 같으면 **받은 `record` 를 그대로 돌려주게** 한다. 그 한 가지로 위 넷이 전부 따라 풀린다. 비교할 값은 `devStatus`, `opt`, `stage`, `processReached` 네 개와 `tech.optionProgress`, `tech.actual.balance` 둘이다. 같이 `diffByKey` 맨 앞에 `if (old === item) return` 을 넣는다.

> 주의. `stage` 와 `devStatus` 를 자동으로 내리지 않는다는 R298 규칙(`CLAUDE.md`)은 그대로 둔다. 바뀐 게 없을 때 같은 객체를 주자는 것이지 계산 규칙을 손대자는 게 아니다.

## 2. DD 전체 열 검색이 한 글자마다 전체를 훑는다 (큼)

`src/routes/DevelopmentMasterSheet.tsx:1882` (같은 스캔이 `3653` 에 한 벌 더 있다)

```
allColumns.some((column) => String(column.value(record, linked) ?? "").toLocaleLowerCase("ko-KR").includes(query))
```

디바운스가 없다. 저장소 전체에 `debounce`, `useDeferredValue`, `startTransition` 이 **한 군데도 없다.** 그래서 글자 하나마다 전체 행 x 74열을 돈다.

여기에 `toLocaleLowerCase("ko-KR")` 가 얹힌다. 재 보니 같은 스캔이 **170.3ms 대 6.6ms** 로 26배 차이다. 한글에는 대소문자가 없어서 로캘을 넘겨서 얻는 것이 사실상 없다. 저장소 전체에 51군데 있다.

바로 아래 줄(`1886`)에는 `allColumns.find` 가 행 루프 **안**에 있다. 열 필터를 하나라도 켜면 행 수 x 필터 수 x 74 가 된다.

**고치는 방향.** 셋 다 따로 효과가 난다. `toLowerCase()` 로 바꾸는 것, 검색어에 `useDeferredValue` 를 거는 것, `allColumns` 를 `Map` 으로 미리 색인해 두는 것이다. 더 하려면 행마다 "검색용으로 한 번 이어 붙여 소문자로 바꿔 둔 문자열"을 `record` 참조 기준으로 캐시한다. 1번을 먼저 고쳐야 이 캐시가 산다.

## 3. 정렬이 `localeCompare` 를 매 비교마다 새로 만든다 (큼)

`compareColumnRows` 의 기본 분기(`DevelopmentMasterSheet.tsx:1872`)가 `String(...).localeCompare(..., "ko-KR", { numeric: true })` 다. 저장소 전체에 `localeCompare` 가 **119군데** 있고 상당수가 `sort` 비교 함수 안이다.

비교마다 로캘 규칙을 새로 세운다. `Intl.Collator` 를 한 번 만들어 재사용하면 800개 정렬이 **95.1ms 에서 2.4ms** 로 떨어진다. 40배다.

**고치는 방향.** 모듈 최상단에 `const KO = new Intl.Collator("ko-KR", { numeric: true })` 를 두고 `KO.compare(a, b)` 로 바꾼다. 결과 순서는 같다. 가장 뜨거운 곳(DD `compareColumnRows`, `ownerOptions`, `optionsById` 의 `sortKo`)부터 하면 된다.

## 4. 팀원 한 명이 고치면 모두의 브라우저가 25개 키를 다시 파싱한다 (큼)

`src/data/firestore-sync.ts:308` `applySnapshot`

컬렉션 전체를 `onSnapshot` 으로 구독한다(`firestore-sync.ts:418`). 문서 하나만 바뀌어도 스냅샷은 전체로 온다. 그런데 **어느 키가 바뀌었는지 보지 않고** 25개 키를 전부 다시 처리한다. 키마다 이 순서다.

1. 청크 문자열을 이어 붙인다
2. `JSON.parse` 한다
3. `mergeForKey` 로 로컬과 합친다
4. `JSON.stringify(nextValue) === JSON.stringify(localValue)` 로 비교한다

4번이 특히 비싸다. 2.5MB짜리 `completed` 하나만 해도 직렬화 두 번에 **20.5ms**, 파싱까지 더하면 약 27ms다. 여기에 `records` 와 나머지 23개 키가 붙는다. 브라우저에서는 **스냅샷 한 번에 100ms 이상 메인 스레드가 멈춘다**는 뜻이다. 팀원이 셀 하나 고칠 때마다 모두에게서 일어난다.

**고치는 방향.** `snap.docChanges()` 로 바뀐 문서만 보고, 그 문서가 속한 키만 다시 조립한다. 이것 하나로 대부분이 사라진다. 비교는 `JSON.stringify` 대신 참조 비교나 길이 비교를 먼저 거쳐 다른 것 같을 때만 깊게 본다. `completed` 는 5,190건이고 거의 안 바뀌는 값이라, 애초에 이 구독에서 뺄 수 있는지도 따져볼 만하다.

**쓰기 쪽은 문제가 아니었다.** `scheduleRecordsSave` 가 500ms 디바운스를 걸어 둔다(`useAppStore.ts:573`). 여기는 손댈 것이 없다.

## 5. 첫 화면에서 안 쓰는 데이터 5MB를 받는다 (큼)

**HOME 이 2.7MB `feed.json` 을 받아 기사 5건만 쓴다.** `Home.tsx:876` 이 받고 `HomeTrendSection.tsx:346` 이 `.slice(0, 5)` 한다. 파일에는 기사가 1,500건 들어 있다. 실제로 쓰는 양은 11,009자로 **전체의 0.5%** 다.

**`archive.json` 2.5MB 를 쓸지 안 쓸지 정하기 전에 먼저 받는다.** `App.tsx:146` 이 `await loadLedgerArchive()` 를 먼저 하고, **그 다음 줄에서** 기존 `completed` 가 있는지 본다. 이미 값이 있으면 받은 2.5MB를 버린다. `cache: "no-cache"` 라 매번 서버에 물어본다. 그리고 이 `await` 가 끝나야 `hydrated` 가 서고, 그래야 Firestore 동기화가 시작된다(`App.tsx:168`). 쓰지도 않을 파일이 실시간 동기화를 붙잡고 있다.

**고치는 방향.** HOME 용으로 상위 몇 건만 담은 작은 파일(`feed-home.json` 같은 것)을 수집기에서 같이 떨구고 HOME 은 그것만 받는다. TREND 화면에 들어갈 때만 전체를 받는다. 아카이브는 `completed` 가 비었는지 **먼저 보고** 비었을 때만 `fetch` 한다.

## 6. 메인 번들에 화면 20개와 무거운 라이브러리가 다 들어 있다 (큼)

화면 중 `lazy` 는 `/meta` 하나뿐이다(`App.tsx:45`). DD MASTER, 창고, FABRIC REQUEST 를 포함해 나머지 전부가 `index.js` 안에 있다.

라이브러리도 같다. `exceljs` 는 쓸 때 받도록 잘 분리돼 있는데(동적 import 10군데), **`xlsx`(SheetJS)는 10개 모듈에서 정적 import** 라 통째로 들어간다. 그중 `ledger-archive.ts` 는 `App.tsx` 가 부팅에 쓰는 모듈이다. `recharts` 와 `firebase` 도 정적이다.

결과가 gzip 986KB, 원본 3.22MB다. 사무실 PC에서 파싱과 컴파일에만 1초에서 3초가 든다.

**고치는 방향.** 화면을 `lazy` 로 나눈다. `xlsx` 는 쓰는 자리에서 `await import("xlsx")` 로 바꾼다. `exceljs` 가 이미 그렇게 돼 있으니 같은 모양이면 된다. CLAUDE.md 가 "엑셀 업로드는 쓰지 않는다"고 적어 둔 만큼 이 코드는 초기 경로에 있을 이유가 없다.

## 7. DD MASTER 에 가상 스크롤이 없다 (큼, 다만 순서는 뒤)

`DevelopmentMasterSheet.tsx:3881` 이 `filtered.map` 으로 **걸러진 모든 행**을 그린다. 창고는 가상 스크롤이 있는데(`Warehouse.tsx:198` `ROW_HEIGHT = 32`) DD 는 없다. 800행이면 약 59,000칸이 DOM 에 깔린다. sticky 가 걸린 칸이 많아 레이아웃 비용도 같이 올라간다.

**고정 3열과 행 머리는 `memo` 밖이다.** `GridCell` 로 안 가고 `<td>` 를 직접 그린다(`3941`, `3951`, `3952`). 그래서 화살표 키로 선택만 옮겨도 800행 x 4칸이 다시 그려진다.

`visibleGroups` 와 `displayedColumns` 가 `useMemo` 밖이다(`1847`, `1854`). 매 렌더 새 배열이라 `colIndexOf`, `rect`, `extraRects` 메모가 전부 헛돈다. FABRIC REQUEST 도 같은 모양이다(`FabricRequest.tsx:1237`).

렌더마다 `ddWarnings(record)` 가 행마다 돌면서 날짜 아홉 개를 검사한다(`3883`).

**고치는 방향.** 가상 스크롤은 효과가 크지만 **지금 손대면 위험하다.** R437 의 Alt+Enter 줄바꿈 때문에 행 높이가 고정이 아니고, CLAUDE.md 가 창고에서 같은 이유로 Alt+Enter 를 막았다고 적어 두었다. 높이 실측 기반이어야 해서 작업이 크다. 1번과 2번과 3번을 먼저 고치고 그래도 느리면 그때 간다.

당장 할 수 있는 것은 셋이다. `visibleGroups` 와 `displayedColumns` 를 `useMemo` 로 감싸는 것, 고정 3열을 `GridCell` 과 같은 식으로 `memo` 하는 것, `ddWarnings` 를 `record` 참조 기준으로 캐시하는 것이다. 셋 다 1번을 고친 뒤라야 제값을 한다.

## 9. FABRIC REQUEST 가 렌더 중에 전체를 다시 훑는다 (중간)

`FabricRequest.tsx:2455`

```
const styleStart = slots.findIndex((slot) => slot.style.reqId === style.reqId)
```

이 줄이 `visible.flatMap((style) => ...)` **안**에 있다. `slots` 는 전체 스타일의 전체 옵션이다. 스타일 200건에 옵션 600건이면 렌더마다 120,000번 비교한다. 바로 위 `2446` 의 `visibleColumns.filter` 도 스타일마다 다시 돈다.

**고치는 방향.** `reqId` 에서 시작 인덱스로 가는 `Map` 을 루프 밖에서 한 번 만든다. `optionColumns` 도 루프 밖으로 뺀다.

## 막다른 길로 확인한 것

찾아봤는데 문제가 아니었던 것들이다. 다시 뒤지지 않도록 적어 둔다.

- **Zustand 셀렉터는 깔끔하다.** 전체 스토어를 구독하는 곳은 `DataProtectionPanel.tsx:61` 하나뿐이고 설정 화면이라 상관없다. 객체를 돌려주는 셀렉터는 없다.
- **표의 `key` 는 안정적이다.** `rowId`, `item.key`, `reqId`, 열 id 를 쓴다.
- **Firestore 쓰기는 이미 디바운스가 있다**(500ms).
- **`exceljs` 는 이미 동적 import 다.** 문제는 `xlsx` 쪽이다.
- **레이아웃 상시 컴포넌트(Topbar, 사이드바, MemoDock)는 `records` 를 구독하지 않는다.** 편집할 때 화면 껍데기가 같이 다시 그려지지는 않는다.
- **`ResizeObserver` 와 전역 리스너에 cleanup 이 있다.** 새는 곳은 못 찾았다.
- **`edgeStyle` 과 `moveStyle` 은 대부분 `undefined` 라** `GridCell` 의 `memo` 를 깨지 않는다. 여기는 잘 짜여 있다.

## 교차 검증 기록

클로드와 코덱스가 서로 안 보고 따로 봤다. 코덱스는 `gpt-5.6-sol`, 읽기 전용, 추론 강도 high 다.

**둘 다 찾은 것**은 1번(부분), 2번, 4번, 5번, 6번, 7번이다. 이것들은 확실하다고 봐도 된다.

**코덱스만 찾은 것**이 넷이고 **전부 직접 확인했다.**
- 감사 diff 에 같은 참조 건너뛰기가 없다 (`audit.ts:118`). 사실이다
- 창고가 대장을 두 번 만든다 (`Warehouse.tsx:547`, `567`). 사실이다
- FABRIC REQUEST 의 `slots.findIndex` 가 루프 안에 있다 (`FabricRequest.tsx:2455`). 사실이다
- 고정 3열이 `memo` 밖이다. 사실이다. `<td>` 를 직접 그린다

특히 첫 번째가 값졌다. 그걸 따라가다 `recalculateDevelopmentRecords` 가 **안 바뀐 행까지 새 객체를 만든다**는 1번을 찾았다. 이것이 이 점검에서 가장 큰 발견인데, 코덱스는 "전 행을 flatten 한다"는 증상까지만 보고 원인까지는 못 갔다.

**클로드만 찾은 것**은 숫자로 잰 것들이다. `toLocaleLowerCase` 26배, `localeCompare` 40배, HOME 이 받는 2.7MB 중 0.5%만 쓴다는 것, 번들 gzip 986KB, 스냅샷 비교 비용 20.5ms 다. 코덱스는 "소문자 변환"과 "정렬"을 비용으로 적긴 했지만 로캘 인자가 그 비용의 대부분이라는 것은 짚지 못했다.

**코덱스가 틀린 것은 없었다.** 다만 비용 등급을 전부 "큼"으로 몰아서 우선순위를 가리기 어려웠다. 그래서 이 문서의 순서는 측정값으로 다시 매긴 것이다.
